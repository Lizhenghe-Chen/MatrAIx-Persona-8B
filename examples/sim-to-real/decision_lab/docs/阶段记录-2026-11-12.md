### 5.3 账单以余额为准，但要先校准

`ops/balance.py` 现在会把每次余额快照写进 `~/.local/share/matraix-decision-lab/balance-ledger.jsonl`，跑前跑后各打一次就能算出真实花费。

已记录的快照之间**对不上**，必须说清：

- 文档早先记过「余额 880.65 → 42.78 元」，据此推出的「wide-v1 约 210 元、单价低估 5 倍」**已撤回**——3.22M token 无论按哪种价目都算不出 210 元。
- 较可靠的一次是 wide-v1 之后余额 42.78 元，此后到 2026-11-12 16:36 之间**没有任何 API 调用**，余额停在 10.19 元，即这 32.59 元只可能是 wide-v1 的延迟结算。折算 $4.6，与按价目算的 $5.05 基本吻合（差 9%，可由缓存折扣解释）。
- 因此**按官方价目乘实际 token 与账单同量级**；之前“低估 5 倍”的结论源于把别处的消费算进了本轮，已撤回。
- 但 8.4 的台账显示它仍可能低估 1.5–2 倍（失败重试的 token 不入库是已知原因之一），所以**账单口径仍以余额快照为准**。
- 仍需你确认一件事：这个 API key 是否还有别的用途（其他应用／其他机器）。若只有本项目用，那么 880.65 → 10.19 的 870 元降幅（≈$122）远大于全项目 27.6M token 对得上的约 $31，缺口只能来自别处。

**当时的余额是 10.19 元**（写作时点）；用户随后充值到 998.13 元，本节结余数字以 8.4 为准。

**"方向对"是及格线不是优势**——查表法方向同样对且更准。分位划分是事后分解，不能当"事先挑人"的规则。

### 8.2 付费：anchor-v1（信息对等实验）

- 冻结 576 条请求；190 条与 wide-v1 字节相同直接复用；实际新调用 380 次；58 次失败全部经保留记录恢复；23 条因概率和微偏离做了重新归一化并计数。
- 德国番茄：优化 0.682 → 给分布 0.512 → 直接用分布 0.504（**打平**，区间跨 0）。
- 美国网购与达人：优化 0.500 → 给分布 0.417 → 直接用分布 0.384（**仍显著落后 8.7%**，限幅版缩到 4.3% 不显著）。
- 限幅（±15pp）带来的额外收益只有 0.2% / 4.1%，均不显著。

**一句话**：差距的一大半来自"模型不知道基础比例"，把它补上后 AI 从"输 35%"变成"打平或小输"；但**人格画像在已知基础分布之上没有可测量的增量**。过度自信（压扁）不是主因。

### 8.4 余额与费用（台账实测）

用户充值后余额 998.13 元；anchor-v1 前后两次快照：**998.13 → 975.45，实付 ¥22.68（≈$3.19）**。

对账结果（这一轮第一次能用台账校验价目估算）：

| 口径 | 数值 | 说明 |
|---|---|---|
| 台账实测 | **¥22.68（$3.19）** | 唯一可信的账单数字 |
| 按价目×已记录 token | ¥12.27（$1.73） | 380 次付费调用的 usage 合计 1,631,698 token |
| 差额 | 约 ¥10 | 58 次失败重试的 token **没有被记录**（解析失败时原始响应未留存），按同规模估算约 ¥3–4；其余差额未能归因 |

**结论修正**：价目估算与实际同量级（1.5–2 倍以内），但**不能当账单**；`ops/balance.py` 的前后快照才是账单口径。这比早先"低估 5 倍"的说法温和，也比"按价目就行"更保守——两种极端都撤回。

小额换算：本轮 438 次实际请求（380 完成 + 58 重试）≈ ¥0.05/次，可作为后续预算的单价参照。
